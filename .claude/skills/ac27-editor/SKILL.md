# AC27 Editor — Repo Skill

## Project Identity

- **Name:** `ac27-editor`
- **Purpose:** Cross-platform desktop level editor for Airport Control 27 `.acl` flight schedule files
- **Stack:** Electron 33 + React 19 + Vite 8 + zustand 5
- **Entry:** `electron/main.js` (Electron main process) + `src/main.jsx` (React renderer)
- **App ID:** `com.ac27.editor`
- **MCP Integration:** Built-in HTTP API server (port 31415) + MCP tools for AI agent control (see `ac27-editor-mcp` skill)
- **Cloud LLM Chat:** In-app chat panel powered by DeepSeek / Gemini / Claude / Codex — 4-vendor multi-model chat with tool calling (see `references/mcp-integration.md`)

## Schema

All `.acl` files use the **v4 schema** — a GATCARC4 binary container (introduced by the 2026-07 game update). v4 is the only format: there is no schema detection and no `isV4` flag anywhere in the code. Every parse/extract/build path goes through `buildPkIndex()` → `PKStaticEntities` + `$blobdoc` navigation.

- **Binary container:** Files are stored on disk as GATCARC4 binary (magic "GATCARC4", SHA-256 payload integrity, append checkpoint frames). `readAclText()` decodes to Odin JSON text; `writeAcl()` re-encodes preserving the on-disk format.
- **Flight plans:** Flight-plan entries live in `StaticData.$blobdoc.StaticItems.$rcontent` with `flight-plan:` key prefix. Uses `InitialArrival`/`InitialDeparture` field names. InBlockTime/TakeoffTime always 0 (game computes dynamically).
- **Type numbering:** `$blobdoc` sections have **independent type numbering** from the outer document. Type N inside a `$blobdoc` can mean a completely different type than type N outside it. Both save and load paths maintain separate type maps (per segment in the save pipeline).
- **Frontend integration:** Hides InBlockTime/TakeoffTime columns. Skips time-order validation (InBlockTime/TakeoffTime always 0/unset). New flights skip InBlockTime/TakeoffTime defaults.
- **No pre-spawned aircraft:** Files have no WorldState section and no pre-spawned State=30 or State=5 aircraft. Approach/State-5 extraction functions (`extractApproachData`, `extractState5Data`) return empty.
- **Designator mapping — two-pass with jetway fallback:** `buildDesignatorMapping` cross-references `StaticItems` (flight-plan → Registration, AircraftType, Stand) with `RuntimeEntities` in two passes to build the `AircraftType → Designator` map. **Pass A** scans `aircraft:REG` entries for `Specification.Designator` (linked via Registration). **Pass B** scans `jetway:STAND` entries for `DockingAircraft.Specification.Designator` (linked via Stand → AircraftType from the static-item `Stand` field). This handles aircraft whose only runtime representation is inside a jetway's `DockingAircraft` rather than as a standalone `aircraft:REG` entry. Produces a complete map for spec lookup during save.
- **Runway pairs from static PK entities:** `extractV4RunwayPairs(aclText)` (in `src/acl/utils.js`, re-exported via the parser facade) derives the runway-change pair options for the RunwayEditor from the static runway objects in `PKStaticEntities` — each physical runway ("4L/22R") appears as two `"$k": "runway:*"` entries sharing a `PhysicalName`, yielding the reciprocal pair `4L|22R` + `22R|4L`. This **replaces** the old timeline-change scanning (`collectRunwayPairs`), which found nothing on airports that never defined runway changes (KJFK, KDCA) and hid the runway editor behind `hasPairs=false`. `electron/main.js` calls `extractV4RunwayPairs` on the first ACL in `_collectAirportRunwayPairs` (`collectRunwayPairs` remains only as a fallback if extraction throws). Note the flag-clearing rule in `useEditorSaveActions.jsx`: `timelineModified.runway` must be cleared on save regardless of `runwayTimelinePath` (the ACL patch in `save-acl` always runs; most real levels have an empty `Config.runwayTimelineFile` → no sidecar JSON → previously the flag stayed set and back-navigation falsely reported unsaved changes).
- **Stand alias registration in designator mapping:** the `Stand → AircraftType` map used by Pass B registers **alias forms** of each flight-plan stand so the exact jetway-key lookup resolves — flight plans say `"31"` while jetway keys are `"31A"`/`"31B"`, or `"07"` vs `"7"`. For stands with a numeric prefix, aliases are: the raw string, the un-padded number, the zero-padded (2-digit) number, and each with `A`/`B` suffixes; **first-registered wins per alias** (flight-plan scan order). Non-numeric stands (e.g. `"it4-38"`) register only their exact string — no suffix aliases. Note: a stand's aliases claim its sibling sub-position names too (`"31"` claims `"31A"`+`"31B"`; `"1A"` claims `"1B"`), so when sibling jetways host different aircraft types the first-scanned type wins for the whole family.
- **Specification extraction:** `extractSpecificationDB` scans the entire decoded text for `Specification` objects inside jetway `DockingAircraft` entries and `RuntimeData` aircraft entries. A fallback `_extractFallbackSpec(text)` extracts a single spec from arbitrary text when the approachCache specDB/designatorMap are unavailable.
- **fmtFloat3 format change:** Both `buildApproachAircraftBlock` and `buildState5AircraftBlock` now emit `float3` values without named fields — `v.x, v.y, v.z` instead of `"x": v.x, "y": v.y, "z": v.z` — matching the actual Odin serialization format. Five empty string-array fields in the `RunwayCoordinator` now share a single `$id` via `$iref` references instead of each getting a unique `$id`.
- **Stand heading from TailPosition→NosePosition:** Stands link to taxiway nodes via `$iref` references (`TailPosition`/`NosePosition`). The `_parseStandPositions` path resolves these `$iref` values to coordinates and computes the heading from the tail→nose vector (`Math.atan2(-dz, dx)`), producing `{ x, y, heading, tailX, tailZ, noseX, noseZ }`.
- **Stand nose/tail-based aircraft positioning:** Both `_buildStandaloneAircraftEntry` and `_buildActiveJetwayEntry` compute aircraft parking position and direction directly from stand nose/tail coordinates instead of using the cached heading or hardcoded defaults. The formula is `direction = normalize(NosePosition - TailPosition)` and `position = NosePosition - WheelBase * direction`, where `WheelBase` is read from the aircraft's `spec` (defaults to 0 if unavailable). In `_rebuildStaticDataSections`, stand positions are parsed once via `_parseStandPositions(text)` upfront and passed as the `standPositions` parameter to all jetway rebuild calls — replacing both the old `atan2(-dz, dx)` heading-based direction (standalone entries) and the hardcoded `(-5.72, 0, -12.54)` / `(0.422, 0, 0.906)` defaults (jetway entries). Jetway position lookups try multiple key formats (numeric parse, raw string, zero-padded) for robustness.
- **Save pipeline cleanup:** After rebuilding StaticData (step 7), `_rebuildStaticDataSections(aclPath, flights, undefined, approachCache, aclcfgStartTime, _saveSec)` runs a multi-stage cleanup across ALL segments (header blobdoc + checkpoint frames). Before modifications begin, `_validateStandConflicts()` checks all flights for stand occupancy conflicts (consecutive ARR→DEP pairs must have matching registrations — different aircraft cannot occupy the same stand simultaneously). Then each GATCARC4 segment is an independent Odin binary document with its own type numbering and `$id` namespace, so the pipeline creates **per-segment type maps** and **per-segment `_IdMapper` instances** for centralized `$iref` remapping. The resolved `saveSec` (from `aclcfgStartTime`, falling back to `resolveConfigTime` — `_saveSec` is ignored) is threaded through to `_rebuildFlightRuntimeEntities` for aircraft position computation. Execution order (critical — 7b MUST run before 7a so jetway detection sees intact `$fstrref` values):
  1. **7a-2. Pre-expand short-form $type refs:** Expands bare `$type: N` references to fully-qualified strings **before** any cleanup steps that might remove type declarations. Uses per-segment type maps so each segment's own declarations are used. Bare refs surviving in KEPT entries are re-expanded in 7b-2.
  2. **7a-3. Pre-compute flight-plan `$id` map (`fpIdByReg`):** Scans each GATCARC4 segment for its highest existing `$id` value — inflated to `entryId + 38` for `jetway:` entries (a conservative ceiling covering every rebuilt jetway's sub-object range; all rebuilt sub-object `$id`s are now allocated from the segment's dynamic allocator seeded above this max) — then assigns flight-plan IDs at `maxId + 1 + i` for each registration (sorted). This `fpIdByReg` map is shared by both jetway rebuild (7b-1) and flight-runtime rebuild (7b-3) so they use identical `$id` values for `_flightPlan` entries. Jetway inline `_flightPlan` (emitted first in `$rcontent`) gets `$id: fpId`; the top-level `flight-plan:REG` entry (middle) becomes `{ __iref: fpId }` pointing back to it; standalone aircraft (bottom) also use `_flightPlan: { __iref: fpId }`. All `$iref` refs are backward, so `_reorderIrefEntries` processes them with zero deferrals.
  3. **7b-1. Rebuild jetway entries constructively (`_rebuildJetwayEntries`):** Replaces the modification-based `_resetFrameJetwayDockingState` with a **constructive** two-pass approach. Pass 1 parses all RuntimeEntities entries structurally (tokenizer), building a stand→flight lookup from DEP flights (when multiple DEPs share a stand, keeps the earliest OffBlockTime). Also builds a stand→arrivals lookup for **turnaround detection**: when a stand hosts both an ARR and DEP for the same aircraft (matching registration) and the arrival lands before the departure off-block, the jetway is left empty (aircraft hasn't arrived at the gate yet). For DEP flights on matching stands, `_buildActiveJetwayEntry()` generates a complete ~35-field Aircraft structure inside DockingAircraft from a hardcoded template. For stale/empty jetways, a clean cleared-state template is used. Claims shared canonical empty-array `$id`s — the six `RunwayCoordinator` `string[]` fields, `AircraftEvent[]` for `_receivedEvents`, `ECommand[]` for `_waitingForCommands` — from a per-segment dynamic allocator: the first aircraft entry that emits one defines it inline, every later entry `$iref`s it. Ids come from the shared allocator (seeded past the segment's max static `$id` incl. rebuilt-jetway expansion and past `fpIdByReg` ids), NOT from entryId+offset ranges — those overlap between adjacent jetways (entryIds 8 apart, template offsets up to 38: jetway:01 `id(33)=36` equals jetway:02 `id(25)=36`) and a duplicate `$id` that is an `$iref` target crashes the game's JsonDataReader with a NullReferenceException.
  3. **7b-2. Re-expand bare $type refs (belt-and-braces):** Re-runs `_expandShortFormTypes` on segments modified by 7b-1. Since the DockingDoorIndex fix, rebuilt jetway entries inject **full-form self-declaring** `"$type": "N|Name"` values (resolved by canonical name against the segment scope) — no bare integers 3-6 are emitted. The pass survives as a safety net for bare refs remaining in KEPT entries, expanded against the 7a-2 pre-modification typeMap.
  4. **7b-3. Rebuild flight-plan, aircraft, and animator RuntimeEntities (`_rebuildFlightRuntimeEntities`):** Deletes ALL existing `flight-plan:REG`, `aircraft:REG`, and `aircraft-animator:aircraft:REG` entries and rebuilds them from editor state in 4 passes — now using **structured JS objects** + `serializeUnityJson()` instead of template-literal string concatenation. Pass 1: remove old entries (stored as raw text to avoid lossy roundtrip), collect old `$id` for iref remapping. Pass 2: rebuild `flight-plan:REG` entries as structured objects with `$type`, `__v` for DateTime ticks, `__fstrref` for static-item references. Jetway-mapped flights (reg has a jetway entry) get `$v: { __iref: fpId }` instead of a full flight-plan object. Pass 3: build `aircraft:REG` entries via `_buildStandaloneAircraftEntry` using structured objects (spec, dynamics data, runway coordinator, position/direction — all JS objects with sentinel properties). Pass 4: build `aircraft-animator:aircraft:REG` entries. **No more hardcoded ordering:** all entries, including kept entries (raw text preserved), are wrapped in `OdinEntry` objects and passed through `_reorderIrefEntries` for topological sort by `$iref` dependency. Entries with no unresolved `$iref` targets emit in input order; entries waiting on a forward `$id` defer until it appears.
  5. **7c. Remove orphaned RuntimeEntities (`_removeOrphanedFlightEntities`):** Removes/renames entries whose `$k` key (`flight-plan:REG`, `aircraft:REG`, `aircraft-animator:aircraft:REG`) references a registration that no longer exists in the rebuilt StaticItems. On registration rename, updates the `$k` value using the renameMap. Handles fallback via `StaticItem.$fstrref` for already-corrupted saves. Updates `$rlength` counters. Safe because aircraft `$id` namespace lives in jetway `DockingAircraft` (preserved by 7b-1), not in the orphaned `aircraft:REG` entries.
  6. **7d. Cleanup EventLog LatestEvents (`_cleanupEventLogLatestEvents`):** On every save, **fully clears** the `LatestEvents` dictionary inside `singleton:event-log.$v.LatestEvents` — sets `$rlength` to 0 and clears `$rcontent` to `[]`. This replaces the old selective-key-removal approach (which tracked `validRegs` and `renameMap`) with a full wipe, preventing stale `aircraft:REG` entries from accumulating across saves. Invisible to step 7c because it lives deeper inside `singleton:event-log.$v.LatestEvents.$rcontent`.
  7. **Centralized $iref remapping (`_IdMapper.remapIrefs`):** After all rebuild steps, applies old→new `$id` mappings collected by per-segment `_IdMapper` instances. Corrects `$iref` references in preserved entries that pointed to removed/rebuilt objects (e.g. flight-plan `$id` values that changed during 7b-3). The `_IdMapper` class acts as a union-find structure with transitive chain resolution and back-to-front positional replacement.
  8. **7a. $fstrref cleanup & remapping (runs AFTER 7b):** IndexOf-based positional scanning for `$fstrref:"flight-plan:REG"` references — replaces with `null` for deleted registrations, remaps to the new registration for renamed ones. Runs after 7b so the jetway rebuild step can detect stale DockingAircraft via intact `$fstrref` values before they are nulled.
  - **Registration renames:** When a flight's CallSign stays the same but its Registration changed, the pipeline detects this by matching old entries' CallSign (extracted from `InitialArrival`/`InitialDeparture`) to new flights' CallSign, building a `renameMap` that feeds into steps 7c/7a to avoid unnecessary data loss.
  - **New constants:** `DEPARTURE_TAXI_SECONDS` and `ARRIVAL_TAXI_SECONDS` in `src/utils/constants/timing.js` provide per-airport overrides for estimated OffBlockTime→Takeoff and LandingTime→InBlockTime durations. Values are **medians measured from production saves** — ZSJN: 464s dep / 372s arr, KJFK: 404s dep / 456s arr, `default` 400s both (fallback for airports without data, e.g. KDCA whose saves are clean starts). Measured via `tests/_debug/extract_aircraft_times.js` (decodes all `.acl` under `Airports/<ICAO>/Levels/`, extracts per-aircraft `_departureTakeoffTime`/`_arrivalInBlockTime` from RuntimeEntities + `OffBlockTime`/`LandingTime` from StaticItems → `aircraft_times_report.tsv`) then `tests/_debug/compute_taxi_constants.js` (per-airport median/avg, prints ready-to-paste constant blocks). Used by `_computeTakeoffTicks` / `_computeArrivalInBlockTicks` — lookup is `TAXI_SECONDS[icao] ?? TAXI_SECONDS.default`. `TAXI_SPEED`, `POSITIVE_TAXI_ACCEL`, `NEGATIVE_TAXI_ACCEL` (also from `timing.js`, re-exported via `constants.js`) supply aircraft dynamics values for `_buildActiveJetwayEntry` and `_buildStandaloneAircraftEntry`. `DYNAMICS_POSITIVE_TAXI_ACCEL` (3) / `DYNAMICS_NEGATIVE_TAXI_ACCEL` (-4) in `src/utils/constants/aviation.js` are the boosted dynamics override, verified against healthy game saves: `DynamicsPositiveTaxiAcceleration`/`DynamicsNegativeTaxiAcceleration` use them for final-approach aircraft (`dynState === 2`, `aircraftState === 5` — these decelerate hard on the approach path) and fall back to the static (1/-2) values otherwise.
  - **`GRACE_TTL` changed to -60:** Aircraft that landed up to 60 seconds before the snapshot time are now filtered out of approach generation (was -10s). Gives more margin for aircraft that recently touched down, preventing them from appearing on approach with near-zero altitude.
  - **Scenario end +30 min grace for flight times:** All three enforcement points — UI `runTripleValidation` (`src/utils/validators.js`), server `validateFlightObjects` (`electron/api-server.js`), and the clock-popover bounds `getTimeValidationBounds` (`src/utils/timeUtils.js`) — accept primary flight times up to `_configEndTime + SCENARIO_END_GRACE_MIN` (30 min, `src/utils/constants/timing.js`); the game allows events past scenario end. The lower bound `_configStartTime` stays strict, and timeline/runway-change bounds are NOT relaxed. `get_airport_info` reports the effective bound as `timeRules.maxTime`.
- **Blobdoc scope-aware $type expansion:** The `_expandShortFormTypes` function was refactored into `_expandWithBlobdocScopes` (recursive scope-aware walker that identifies `$blobdoc` entries, extracts their type declarations, and recurses for nested blobdocs) + `_replaceBareTypeRefs` (single-scope regex expander). Each `$blobdoc` section has independent type numbering, so bare `$type: N` inside a blobdoc must expand using that blobdoc's own type declarations — not the outer document's.
- **GameTime.CurrentDateTime parsing:** `extractCurrentDateTime(aclText)` tries `GameTime.CurrentDateTime` first (snapshot time, parsed from nested ticks), falls back to `MetaData.BaseTime`. Used by `resolveConfigTime` to override config startTime with post-warmup time (rounded UP to the next whole minute via `roundSecondsToMinute(cdt.secSinceMidnight, true)` — see `timeUtils.js`).
- **Structured object entry building:** `_buildStandaloneAircraftEntry`, flight-plan entries, and animator entries now build **structured JS objects** with sentinel conventions (`__v` for bare values, `__iref`/`__fstrref`/`__eref`/`__guidref` for Odin references) rather than joining template-literal text strings. These are serialized via `serializeUnityJson()` which handles indentation, `$type`/`$id` ordering, and reference token emission. This eliminates the fragile string-formatting code that was error-prone to maintain. Type strings are now bare values (e.g. `'7|ContextCross.Aircrafts.Aircraft, GroundATC.Core'`) — `serializeUnityJson` adds the surrounding quotes automatically.
- **`$iref` topological sort (`_reorderIrefEntries` + `OdinEntry` class):** The old hardcoded ordering (flight-plans FIRST → aircraft/animator → kept) is replaced by a topological sort of all RuntimeEntities entries. `OdinEntry` is a lightweight wrapper around a parsed entry with lazy-serialized text, lazily-computed `$id`/`$iref` arrays. `_reorderIrefEntries` walks entries in a single pass: self-contained entries (all `$iref` targets satisfied by their own `$id`s or in `externalIds`) emit immediately; entries with unresolved `$iref` targets are deferred until the declaring `$id` is seen. `externalIds` is pre-seeded from the parent dictionary structure (`comparer`, etc.) so references to entries outside `$rcontent` are never misidentified as forward refs. Circular/missing `$id` references are logged as errors and appended as fallback.
- **Odin recursive-descent parser (`parseOdinValue`, `parseOdinObject`, `parseOdinArray`):** A complete string-aware recursive-descent parser added to `acl_json.js` that handles the full Odin JSON dialect: typed-value objects (`$type` + bare values → `__v`), Odin reference tokens (`$iref:N`, `$fstrref:"..."`, `$eref:N`, `$guidref:GUID` → sentinel objects), nested objects and arrays (recursively parsed), bare values (`null`, `true`, `false`, numbers, strings), and proper `\uXXXX` escape handling. No regex on the parse path for correctness. Used primarily by `_reorderIrefEntries` to extract `$id`/`$iref` metadata from kept entries — the entry's original text is preserved for output. Export through `src/acl/parser.js`.
- **Kept entries preserve raw text:** Entries that pass through the rebuild (jetway, radio-channel, singleton, etc.) are stored as raw Odin text and emitted verbatim. This avoids lossy reconstruction of deeply-nested `ReactiveProperty<Aircraft>` structures where `_fixTypedValues` doesn't recursively handle all edge cases. Only metadata (`$id`/`$iref` values) is extracted via `parseOdinObject` — the text is never modified.
- **Pre-computed `fpIdByReg` — unified flight-plan `$id` across rebuild steps:** Both `_rebuildJetwayEntries` and `_rebuildFlightRuntimeEntities` receive the same pre-computed `fpIdByReg` map, ensuring the jetway inline `_flightPlan`, the top-level `flight-plan:REG` entry, and the standalone aircraft's `_flightPlan` all share one canonical `$id` per registration. This eliminates the old pattern where jetway entries used `entryId + 16` while flight-plan entries used a separate sequential counter — two different `$id` values for the same logical flight plan. The pre-computation scans each segment for `maxId` and assigns IDs at `maxId + 1 + i` for sorted registrations, guaranteeing no collision with existing entries. `nextId` is advanced past the pre-computed flight-plan IDs before aircraft/animator entries are built.
- **Shared empty-array `$iref` dedup re-enabled via dynamic allocator (the old inline-only rule is gone):** The original `_rebuildReceivedEventsInEntry` / `_rebuildWaitingCommandsInEntry` sharing crashed Unity's `JsonDataReader` because aircraft entries referenced `$id` values defined inside jetway entries — forward refs appearing later in `$rcontent`. The reintroduced sharing (`rpSharedArr`/`rpStrArr` in `_buildStandaloneAircraftEntry`, `sharedEmptyArrayInner`/`sharedStrArrInner` in `_buildActiveJetwayEntry`) is safe because canonical `$id`s are claimed from the segment's dynamic allocator BEFORE any entry text is emitted, so they always precede the entries that `$iref` them (backward refs only — zero deferrals in `_reorderIrefEntries`). One canonical empty `AircraftEvent[]` / `ECommand[]` / `string[]` per segment: the first emitter writes the inline definition, every later entry emits a bare `$iref`. Non-empty content (State=5 `_waitingForCommands = [CMD_CONTACT_TOWER]`) is never shared — it stays inline at its own id and does not claim the canonical definition.
- **`fpTypeStr` regex tightened:** The `$type` extraction in `_rebuildStaticDataSections` now only accepts the expanded `"N|TypeName"` form. A bare `"$type": N` would not self-register in the blobdoc scope, causing "unknown type id N" during Odin binary encoding. The default `fpTypeStr` is already the correct expanded form via per-file typeMap lookup.
- **Preprocessor additions:** The preprocessor gained passes for: (0) `_fixOdinReferences` — string-aware transformation of `$iref:N`, `$fstrref:"..."`, `$eref:N`, `$guidref:GUID` → sentinel objects for `JSON.parse`; (1.5) `_fixMissingCommas` — inserts missing commas between properties; `_collectBareValues` now handles `null`/`true`/`false` as bare values and recursively fixes typed values inside nested objects and arrays.
- **SPECIAL_KEYS updated:** Added `__iref`, `__fstrref`, `__eref`, `__guidref` to the set in `src/utils/constants/acl-format.js`.
- **Strict type resolution from segment type maps:** ALL type numbers come from the per-segment type map (`segTypeMap` / `jwTypeMap`) — no hardcoded ids anywhere. `_makeJwTypeResolver` is the single shared resolver: `_buildStandaloneAircraftEntry` and `_rebuildFlightRuntimeEntities` use unquoted mode (bare `N|Name`, the serializer quotes it), `_buildActiveJetwayEntry` the quoted full-form mode. This prevents type-id-reclamation collisions with kept entries already expanded to full form by `_expandShortFormTypes`. **STRICT: a canonical type name missing from the segment's declarations throws `[TYPE-ASSERT]`** with the name and a scope dump — fallback ids are never minted (silent fallbacks masked the DockingDoorIndex bug class; the old `_freshNum` counter is gone).
- **No fallback type numbers — throw on missing:** The old `_tn(search) || nextFallbackNum++` pattern (`TYPE_NUM_FALLBACK_START` in `acl-format.js` is now a dead export) is gone entirely. `_rebuildStaticDataSections` resolves blobdoc-scoped types (DateTime, FlightPlanArrivalLeg, FlightPlanDepartureLeg, FlightPlanStaticItem) via `_assertBdTn(search, label)` — it searches the blobdoc scope first, falls back to the file-global map only when the matching number is unclaimed in the blobdoc (a checkpoint frame can claim the same number for a different type), and throws a `[V4-BUILD]` error with a scope dump when neither declares it. FlightPlanStaticItem moved onto this path (it previously used the `_tn` boundary-aware matcher + fallback numbering). In `approach.js`, the `ns(num, name)` helper was replaced with `resolve(key, fullName)` that throws if the key is missing from `typeNums`. Hardcoded fallback defaults (e.g. `33` for AircraftState) are eliminated entirely — types must be present in the per-file type map or the build fails early with a clear error.
- **Approach-builder type numbers from per-file typeNums (never hardcoded):** `buildApproachAircraftBlock` and `buildState5AircraftBlock` resolve **every** `$type` — including `vec3` (`UnityEngine.Vector3`) and `strArr` (`System.String[]`) — from the per-file `typeNums` map. The old hardcoded `"16|UnityEngine.Vector3, UnityEngine.CoreModule"` / `"8|System.String[], mscorlib"` were wrong for real files (ZSJN-Morning declares Vector3 at 17 and String[] at 16; 8 is declared nowhere), and BCL ids are not stable across Unity versions. Missing keys throw via `resolve(key, fullName)`.
- **Base-time extraction is `$type`-agnostic:** `_extractBaseDateFromText` matches `"BaseTime": { "$type": <any-id>, ticks }` and WorldState flight times with `"\$type": \d+` — DateTime ids are per-scope, so a hardcoded `$type: 3` silently missed files that declare DateTime elsewhere.
- **`CANONICAL_SCOPE` fixture for builder unit tests:** `tests/integration/_canonical_scope.cjs` exports the ZSJN-Morning frame-scope type declarations (ids 0–54). Unit tests that drive `_buildActiveJetwayEntry`/`_buildStandaloneAircraftEntry` must pass it as `jwTypeMap`/`segTypeMap` — strict resolution asserts `[TYPE-ASSERT]` on any canonical name the scope doesn't declare, so `new Map()` no longer works. Derived via `tests/_debug/dump_frame_scope.cjs`; duplicate names keep last-in-text-order semantics (AircraftEvent[] at 1 and 28 → resolves to 28).
- **Missing DockingPositions hard error:** Both `_buildStandaloneAircraftEntry` and `_buildActiveJetwayEntry` throw an `Error` when `spec.DockingPositions` is missing or empty — instead of silently falling back to a hardcoded default `[{ x: -1.742, y: 2.68, z: 14.75, w: 90 }]`. The error message includes the aircraft type name, identifying the missing type in the approach cache specDB early during save.
- **Spec fields are REQUIRED — no silent defaults (`requireSpecField`):** Generalizes the DockingPositions rule to every spec field. `requireSpecField(log, ctx, field, value, spec, fallback)` (in `src/acl/approach.js`, exported) asserts when a resolved field value is missing — `DEFAULT_*` constants are **message content only, never emitted values**. Applies on intake (`extractSpecificationDB`, `_extractFallbackSpec`) and on emission (`buildApproachAircraftBlock`, `buildState5AircraftBlock`, `_buildStandaloneAircraftEntry`, `_buildActiveJetwayEntry`). The assert message names the exact failure chain: builder, registration, AircraftType, designator, lookup trace (`designatorMap[x]=y; direct specDB[x]=hit|MISS; vBlock fallback=hit|MISS`), refused fallback, and a raw spec preview.
- **AerodromeCode from spec data (never hardcoded 67):** The game uses `AerodromeCode` (ASCII ICAO aerodrome reference code: 67='C' narrowbody, 69='E' widebody, 70='F' 748/388-class) for stand/jetway compatibility. Both builders used to emit 67 for every aircraft, mislabeling widebodies (B789/A333/B77W) in saved output. Now the emitted value is `spec.AerodromeCode` resolved through the normal spec chain — a spec missing it asserts via `requireSpecField` (refusing fallback 67).
- **Every rebuilt jetway sub-object `$id` from the segment's dynamic allocator:** The old static `entryId + offset` scheme collided across jetways — entryIds are 8 apart but template offsets run up to 38. In fails.acl, `jetway:09 id(15) = 190 + 15 = 205` equals `jetway:12 id(3) = 202 + 3 = 205`; a duplicate `$id` that is an `$iref` target makes the game's JsonDataReader bind the **first** declaration (first-wins), so `aircraft:B-5380A`'s `$iref:205` resolved to a `String[]` wrapper → "Data layout mismatch; skipping past node boundary when exiting array". Now `_buildActiveJetwayEntry` allocates every sub-object id from the segment's dynamic allocator (shared with the canonical-array caches, seeded past all static/flight-plan/canonical ids) and registers each old `entryId+offset` id in the segment `_IdMapper`, so the centralized remap step rewrites `$iref` references in preserved entries. The no-cache/defensive path derives a segment-wide allocator past the segment's max `$id`.
- **Jetway field `$type`s resolved by NAME (`_makeJwTypeResolver`):** Type ids are per-blobdoc and vary between files — `R3.ReactiveProperty<Int32>` is id 6 in ZSJN-Morning but id 29 in ZSJN_taixwayclosed, where hardcoded id 6 means `ContextCross.Aircrafts.Aircraft` (writing id 6 for `DockingDoorIndex` misbinds it). `_makeJwTypeResolver(jwTypeMap, quoted=true)` (exported from `flight_plans.js`) builds a name→id lookup from the segment's declarations and returns full-form `"N|Name"` strings; pass `quoted=false` for the object-serializer path, which expects a bare `N|Name` value. **STRICT: a canonical name missing from the scope's declarations throws `[TYPE-ASSERT]`** naming the missing type and dumping the scope (`Scope declarations (N): ...`) — fallback ids are never minted (the old fresh-id counter masked the DockingDoorIndex bug class). **One resolver instance per segment is shared by ALL rebuilt entries (active + empty paths)**. Top-level RuntimeEntity fields resolve the same way (`JW_TYPE_JETWAY`, `JW_TYPE_RP_SINGLE`, `JW_TYPE_RP_AIRCRAFT`, `JW_TYPE_RP_INT32`).
- **State=5 aircraft in standalone entries:** `_buildStandaloneAircraftEntry` now supports State=5 (final approach, DynamicsState=2) aircraft. When `aircraftState === 5`, the entry gets `ApproachDynamicsParams` instead of `FlyApproachDynamicsParams`, with `PathPointList`, `TouchDownPosition`, `ApproachDirection`, and `InitialPosition` fields. State=5 params are resolved from `approachCache.state5ParamsMap` by appKey then runway — throws a descriptive `Error` when no cached entry exists (the old fallback derivation from `AppPointList` was removed; `state5ParamsMap` must always be populated at cache-build time).
- **State=5 `CMD_CONTACT_TOWER` in waiting commands:** State=5 (final approach) standalone aircraft entries now include `CMD_CONTACT_TOWER` in their `_waitingForCommands` array (`__v: [{ $id: id(25), $type: T.cmdArr, $rcontent: [CMD_CONTACT_TOWER] }]`), giving the arrival an initial "contact tower" command. `selectedRunwayExitIndex` is `0` (was `-1` in earlier versions). State=30 (before IAF) and State=10 (DEP parked) entries keep an empty `$rcontent: []`.
- **DEP aircraft in RuntimeEntities:** DEP flights now generate `aircraft:REG` + `aircraft-animator:aircraft:REG` pairs during `_rebuildFlightRuntimeEntities`. Previously only ARR flights got aircraft entries (DEP was assumed covered by jetway `DockingAircraft`). For DEP flights with an active (populated) jetway, the aircraft entry is `$v: { __iref: jetwayAcId }` — pointing into the jetway's inline `DockingAircraft` — avoiding duplication of the large Aircraft object. For DEP flights without a jetway (or on a stale jetway), a standalone Aircraft entry is built with taxi values (speed, acceleration) set to 0 (parked aircraft), `DynamicsParams: null`, `aircraftState: 10` (parked-at-stand), and `gearRatio: 1` (gear down). The `radioChannelId` reference defaults to `null` when no radio-channel entry exists. Standalone DEP aircraft still get a position from `_resolveStandPosition`.
- **FlightPlan unified via `$iref` chain:** The `_flightPlan` field in `_buildStandaloneAircraftEntry` is now always `{ __iref: fpId }` — a thin reference to the flight-plan `$id` rather than an inlined copy of the full FlightPlan object. The canonical FlightPlan data lives in one of two places: (a) inside the jetway entry's inline `DockingAircraft._flightPlan` (jetway-mapped flights), or (b) in the top-level `flight-plan:REG` entry (standalone flights). The `fpId` is pre-computed in step 7a-3 and shared across both rebuild steps, so the `$iref` chain is always valid. All refs are backward (jetway emitted first, then flight-plan entries, then aircraft entries), guaranteeing zero deferrals in `_reorderIrefEntries`.
- **Combined aircraft+animator pair building (PASS 3&4 merged):** PASS 3 (aircraft:REG) and PASS 4 (animator:aircraft:REG) are combined into a single loop producing `acPairs` — each element is a `[aircraftObj, animatorObj]` tuple. This guarantees aircraft and animator entries for the same registration are always adjacent in the output, preventing forward `$iref` issues when the $rcontent order changes. The pair array is flattened into the ordered descriptor list.
- **Partitioned kept entries:** Kept RuntimeEntities entries are now partitioned by `$k` prefix into five buckets: `jetway:` → `keptJw`, `radio-channel*` → `keptRadio`, `singleton:*` → `keptSingleton`, and everything else → `keptOther`. Final assembly order is deterministic: `jetway → radio-channel → flight-plan (new) → singleton → aircraft+animator pairs → other`. All kept entries preserve raw text and only extract `$id`/`$iref` metadata via `parseOdinObject`.
- **`typeNameIndex` in approachCache:** `buildApproachCache` exports `typeNameIndex` (inverted `typeMap`: name→id) and `fileTypeNameIndexes` (per-file name→id Maps). Built by `buildTypeNameIndex(typeMap)` in `approach.js` — first declaration wins per Map.
- **Shared canonical-array caches (`strArrCache`/`recvEventsCache`/`waitingCmdsCache`):** Both `_rebuildJetwayEntries` (7b-1) and `_rebuildFlightRuntimeEntities` (7b-3) receive per-segment cache objects for the shared empty arrays — `string[]` (the six `RunwayCoordinator` fields), `AircraftEvent[]` (`_receivedEvents`), `ECommand[]` (`_waitingForCommands`). All three caches share ONE dynamic `$id` allocator per segment (`{ v }` seeded at `segMaxId + 1`), so their canonical ids can never collide with each other, with static entry ids, or with precomputed flight-plan ids. `canonicalId` (claimed once, by whichever of 7b-1/7b-3 runs first) plus `canonicalEmitted` (whether the inline definition has been written yet) handle the cross-ordering between the two rebuild steps. 7b-3 also advances `nextId` past every claim so aircraft/animator ranges never reach them.
- **Radio-channel type resolution from StaticItems:** During `_rebuildFlightRuntimeEntities`, the code parses `StaticItems.$rcontent` via the tokenizer to build a `radioChannelTypeMap` (key → Type: 2=GND, 3=TWR, 5=APP). Kept radio-channel entries in `RuntimeEntities` are matched by key against this map to identify separate `towerChannelId` (Type 3) and `apprChannelId` (Type 5) — replacing the old single `radioChannelId` which grabbed the first radio entry regardless of type.
- **State-dependent radio channel selection:** `_buildStandaloneAircraftEntry` selects between tower (State=5, final approach) and approach (State=30, before IAF) based on aircraft state. State=10 (DEP parked) stays null. Both `_radioChannel` and `_jurisdictionRadioChannel` are set to the same active channel (previously both were always `null`).
- **gearRatio in animator blocks:** `buildAnimatorBlock` accepts a `gearRatio` parameter (default 1). Gear is down (1) for parked (State=10) and final-approach (State=5) aircraft; gear is up (0) for STAR approach (State=30, before IAF) since landing gear retracts during cruise/descent phase.
- **TouchDownPoint $iref resolution:** `resolveApproachProcedureData` resolves touchdown position from the runway entry's dedicated `TouchDownPoint $iref` pointer instead of extending past the last approach-procedure point by a fixed distance. The `$iref` targets a taxiway-node entity at the landing threshold. Throws on missing or unresolvable `TouchDownPoint`.
- **routeName in approach procedure data:** `resolveApproachProcedureData` extracts and returns the `Name` field from the approach procedure's route entry as `routeName`. `_buildStandaloneAircraftEntry` uses this `routeName` for the `ApproachRoute` field, replacing the old `state5ParamsMap` lookup that used `procedureName|runway` pipe-delimited keys (removed).
- **State=5 `_route` uses approach procedure name:** In `_buildStandaloneAircraftEntry`, State=5 aircraft (final approach) set the `_route` field to `state5Params.routeName` (e.g. `"RNAV ILS Z Rwy 19"`) instead of the STAR name (e.g. `"UBSS6W"`). Non-State-5 entries keep `star`; the guard is `aircraftState === 5 && state5Params && state5Params.routeName`. The jetway DockingAircraft template is unaffected (jetway aircraft are always State=10 parked).
- **hintPosition for approach variant selection:** `computeFullTerminalPath` passes the last FlyApproach point (IAF) as `hintPosition` to `resolveApproachProcedureData`. When multiple Type=1 approach procedure variants exist for a runway, the closest one to the hint position is selected instead of the first variant. Without this, TAT could be misestimated and State=5 aircraft positions could be incorrect when variants have different path lengths.
- **totalLen includes touchdown distance:** `_buildStandaloneAircraftEntry` includes the touchdown distance in `totalLen` (the denominator for `rawTargetDist` IAF boundary). This ensures `totalLen` matches the path length that TAT was calibrated for — scenery-derived TAT includes `tdDist` from `computeFullTerminalPath`. Without this, `rawTargetDist` used a shorter denominator, biasing the IAF boundary toward State=30 for aircraft near the runway.
- **Hardcoded InitialPosition.Y:** `_buildStandaloneAircraftEntry` hardcodes `InitialPosition.Y` to `15.24` (the standard ILS approach ceiling at 100 m/unit scale = 5000 ft) instead of using `state5Params.initialPosition.y || 0`. The stored path points have Y=0 (game engine computes altitude internally from touchDownPosition + path distance), but `InitialPosition` stores the approach ceiling altitude directly. Every original game file uses 15.24 regardless of airport.
- **touchDownPosition from state5ParamsMap:** `_buildStandaloneAircraftEntry` resolves touchdown position from `approachCache.state5ParamsMap` (by appKey then runway) instead of `approachCache.runwayThresholds`. `runwayThresholds` returns an array of two threshold positions, not a single touchdown point — passing it to `computePosition` caused `_vec3Dist` to return NaN (`undefined.x - undefined`), so the touchdown segment was never appended to the path and glideslope Y was wrong.
- **v4 Vector4 array parsing via preprocessUnityJson:** `_extractVector4Array` now uses `preprocessUnityJson` + `JSON.parse` with the `__v` sentinel for v4 files, instead of the old bare-number `_parseBareNumbers` approach. This correctly handles both short-form (`"$type": 11`) and full-form (`"$type": "11|UnityEngine.Vector4, ..."`) type strings in Vector4 array entries, ensuring DockingPositions and similar arrays decode accurately.
- **Unused import removed:** `TAT_FALLBACK_EXTEND` removed from `approach.js` imports — the constant was no longer referenced anywhere in the module.
- **Timeline rebuild via MetaData object (`_rebuildV4TimelineSections`):** `_rebuildTimelineSections(aclPath, weather, wind, runway)` parses the `MetaData` section value with the tokenizer, splices rebuilt `WeatherFrames` / `WindFrames` / `RunwayTimeline` sub-sections in place (`keyStart` → `valueEnd`, keeping the `"MetaData"` key intact), and writes back via `writeAcl`. Mirrors the load → modify → serialize pattern. In v4 files these timeline sections live **inside MetaData**, not at top level.
- **RunwayTimeline type-number conflict fix:** When a file's Timeline is empty, `_metaRunway` falls back to `tlTypeNum + {1,2,3}` for the element type numbers — but those may already be claimed by unrelated types in the outer document (e.g. ZSJN files: type 12 = `System.Byte[], mscorlib` collides with the `tlElemTypeNum = 12` fallback when `tlTypeNum = 11`). The rebuild path scans the full document for used `"$type": "N|"` numbers and bumps each conflicting fallback to the next unused number, emitting the full-form declaration on the first element and bare refs after. Verified on ZSJN: 12/13/14 → 55/56/57.
- **Tokenizer `findKeyAtDepth` string-awareness fix:** `findKeyAtDepth(start, end, key, targetDepth)` now only matches the search key at an opening quote that is OUTSIDE a string (`!inString` at `"`), instead of checking for the key text anywhere at the target depth. Previously, key text appearing inside a string *value* (e.g. a value containing the literal `"FlightPlan"` when searching for `FlightPlan`) could be falsely matched and returned the wrong value range. The key-match check moved into the quote handler before the `inString` toggle; escaped quotes (`\"`) are still skipped by the backslash rule.

## Key Rules for Agents

1. **React + Vite + zustand stack.** Frontend uses ESM, JSX, and React hooks. No global-scope scripts.
2. **No TypeScript.** This is plain JS/JSX. Do not add `tsconfig.json` or convert files to `.tsx`.
3. **No linter/formatter.** Do not add ESLint, Prettier, or any linting config unless explicitly asked.
4. **Testing uses Vitest (component) + Playwright (E2E) + Node.js (integration).** Component tests go in `tests/components/`, electron-backend tests in `tests/electron/` (use `@vitest-environment node` + `require.cache` priming for CJS modules that require ESM SDKs), E2E specs in `tests/e2e/`, integration scripts in `tests/integration/`. Do not add Jest or Mocha.
5. **No npm dependencies for core logic.** The app uses only Node.js built-ins. Justify any new dependency.
6. **Preserve CommonJS for backend.** `electron/` and `src/acl/` use `require()`/`module.exports`.
7. **ESM for frontend.** `src/components/`, `src/hooks/`, `src/store/`, `src/utils/` use `import`/`export`.
8. **IPC for all file I/O.** The renderer never touches the filesystem. All reads/writes go through `electron/main.js` handlers.
9. **Return `{ success }` from IPC.** Every handler returns `{ success: true/false, error?: string }`.
10. **`_underscore` = private in backend.** Prefix internal functions with `_`. Export them anyway for testing.
11. **`snake_case.js` for backend, `PascalCase.jsx` for components.** Match existing conventions.
12. **No inline `style={{}}`.** Always extract CSS to the component's `.css` file.
13. **One `.css` per component.** Match the component filename.
14. **No `dangerouslySetInnerHTML`.** Use `safeHtml()` from `src/utils/safeHtml.jsx` to render i18n strings containing `<strong>`, `<em>`, or `<br>` as safe React nodes. It sanitises unknown tags and attribute injection as plain text.
15. **Use `readAclText()` / `writeAcl()` for all ACL I/O.** Never use `fs.readFileSync(path, 'utf-8')` or `fs.writeFileSync(path, text, 'utf-8')` for `.acl` files. Always go through `gatcarc.js` to transparently decode/encode the GATCARC4 binary container. This applies to `electron/main.js`, all backend modules, and all integration tests.
16. **Use `resolveConfigTime()` for config time display.** Every consumer of ACL config time (startTime/endTime) must use `resolveConfigTime(rawText)` from `src/acl/config.js` — not `_extractConfig()` directly. `resolveConfigTime` applies the GameTime.CurrentDateTime override (post-warmup time), rounded UP to the next whole minute via `roundSecondsToMinute()` from `src/utils/timeUtils.js`. This is the single source of truth. All IPC handlers that read config (`get-file-info`, `load-acl`, `save-acl`, `import-zip`, `restore-latest-backup`, `load-timelines`) already use it.
17. **Update the facade.** New backend modules must be re-exported through `src/acl/parser.js`.
18. **Build locally with `node build.js`** on Windows, never `npm run build:win` (local only — CI uses `npm run build:win` for cross-platform builds).
19. **Bump `CACHE_VERSION` when cache.json schema changes.** Any change to the structure of `approachData`, `fileTypeMaps`, `state5ParamsMap`, `taxiwayPaths`, `sidPaths`, `missedAppPaths`, or new top-level keys in cache.json MUST bump `CACHE_VERSION` in `src/utils/constants/timing.js` (re-exported via `src/utils/constants/index.js` and `src/acl/constants.js` for CJS backward compat). Stale caches silently corrupt saves. Note: `saveTimeOffsets` and `typeMap` are build-time-only and are no longer serialized.
20. **Version tags for releases.** Version tags use `v<MAJOR>.<MINOR>.<PATCH>` (e.g. `v1.2.0`). Keep `package.json` `version` and the git tag in sync. The user decides when to bump; you can re-tag the same version to include new changes.
21. **Keep documentation in sync.** After any significant change, update ALL of:
    - **This skill** (`.claude/skills/ac27-editor/SKILL.md`) and its reference files
    - **README.md**
    - **`tests/README.md`** — whenever tests are added/removed, update the test counts (line 9, line 18, line 22), the file table (add/remove rows), MapWindows file/test counts (line 34), and expected outcomes (lines 44–53). Stale test docs mislead contributors about what's covered.
22. **UDP listener lifecycle is managed by main process.** `startUdpListener()` is called in `app.whenReady()` after `createWindow()`, `stopUdpListener()` in `will-quit`. The listener auto-reconnects on socket errors (2s delay). Do not create multiple listeners or start/stop from the renderer.
23. **Map windows are separate BrowserWindow instances.** They are NOT React components in the main renderer. Track them in `groundMapWindows`/`airMapWindows`/`flightStripsWindows` Maps (keyed by ICAO). Always check for existing windows before creating (focus if exists). Clean up Map entries in the `closed` event handler. Each window loads the same Vite SPA with query params (`?window=groundMap&airport=XXXX`, `?window=airMap&airport=XXXX`, or `?window=flightStrips&airport=XXXX`).
24. **UDP state push handles cleanup.** The `udp-aircraft-state` IPC event is pushed to ALL open map windows every 200ms. Map window components subscribe via `useUdpAircraftState()` hook which wraps `onUdpAircraftState`/`offUdpAircraftState`. Always unsubscribe in `useEffect` cleanup to prevent stale callbacks or memory leaks.
